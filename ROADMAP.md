# Planned work

Each "PySpark 3.5.3 run" below used PySpark 3.5.3 with pandas 3.1.1 on Python 3.13. Each "4.3.0" result used PySpark 4.3.0 with pyarrow 26.0.1 on the same Python and pandas.

## Fixes

- `conditional_column_creation` writes the quote characters into the result. The worked example produces `'Adult'` and `'Senior'` (quotes included) because each value is passed to `when` as a Python string literal. Values should be parsed as SQL expressions or passed as plain values.

- `standardize_data` returns `NULL` for every row of a constant column because the standard deviation (or the range) is 0. SAS's PROC STDIZE says "Constant variables are not standardized." The method should therefore keep a constant column's values as they are.

- `sql_query` and `univariate_analysis` use the notebook's global `spark` session. They should use the DataFrame's own session (`self.df.sparkSession`), such that the class works outside the notebook.

- `rolling_window_analysis` builds its window with `Window.orderBy()` and no column. The row order behind each moving average is therefore not defined. It needs an order-by column parameter, like `ID` in `PROC EXPAND`. PROC EXPAND checks that column: "PROC EXPAND verifies that the ID values are nonmissing and in ascending order." In a PySpark 3.5.3 run ordered by a column with a null, the null row sorted 1st, then entered the average. The method should drop such rows with a warning.

- `split_dataset` is annotated as `-> (pyspark.sql.DataFrame, pyspark.sql.DataFrame)`, which is a tuple of classes, not a valid type hint. The method returns the list from `randomSplit`. The hint should therefore be `List[pyspark.sql.DataFrame]`. The other route is to return a tuple and annotate it `Tuple[pyspark.sql.DataFrame, pyspark.sql.DataFrame]`.

- `frequency_analysis`, `calculate_means`, `cross_tabulation`, `rank_data`, `correlation_analysis` do not follow SAS's defaults for missing values. PROC FREQ leaves a missing value out of the counts and the percentages. PROC MEANS drops a row whose `CLASS` value is missing. PROC TABULATE does the same. PROC RANK leaves a missing value unranked. PROC CORR uses pairwise deletion. Today, the methods count a null as a level, keep a null group, add a `null` row plus a `null` column, rank a null 1st, drop every row that has a null in any of the columns. Each should follow the SAS default. `frequency_analysis`, `calculate_means`, `cross_tabulation` also need an option for SAS's `MISSING` rule. `correlation_analysis` needs one for its `NOMISS` rule.

- A NaN in a float or double column counts as a number, not as missing. In a PySpark 3.5.3 run, `spark.createDataFrame` kept the NaN of a pandas DataFrame (on 4.3.0, Arrow turned it into NULL). A CSV value `NaN` read as a double stayed NaN on both versions. In PySpark 3.5.3 runs on 1.0, 3.0, NaN, `calculate_means` gave a mean of NaN from a count of 3. `frequency_analysis` counted NaN as a level. `rank_data` ranked it last. `sort_data` put it after 3.0. `standardize_data` gave NaN in every row. `handle_missing`, by contrast, filled NaN as missing. SAS has no NaN -- a numeric value is a number or a missing value. SAS says "PROC MEANS excludes missing values for the analysis variables before calculating statistics." The class should turn NaN into null when it reads a DataFrame. A blank string is missing in SAS as well: "A character expression is considered missing if it evaluates to a string that contains all blanks or has a length of zero." In PySpark 3.5.3 runs, an empty string and a string of 2 blanks made 2 levels in `frequency_analysis`, 2 groups in `calculate_means`, 2 columns in each of `cross_tabulation` and `transpose_data`. In `sql_query` on the values a, an empty string, null, `WHERE s IS NULL` found 1 row where SAS finds 2. The same read step should turn an all-blank string into null. Infinity also passes as a number. On inf, 1, 2, null, `calculate_means` gave a mean of inf. `handle_missing` filled the null with inf. None of the SAS pages found says what SAS stores for infinity. The class should raise an error for it.

- `calculate_means`, `standardize_data`, `rank_data`, `rolling_window_analysis` take a string column without an error. In a PySpark 3.5.3 run on the values x1, x2, 10, a group holding x1 and x2 got a NULL mean, a count of 2, the text minimum x1 from `calculate_means`. With 10 in the same group, the mean was 10.0, dropping x1 and x2 without a word. `standardize_data` gave NULL in every row. `rank_data` ranked the values as text. PROC STDIZE says "The VAR statement lists numeric variables to be standardized." Each method should raise an error for a column that is not numeric. Dates, time-stamps, booleans are handled unevenly. SAS keeps a date as "the number of days between January 1, 1960, and a specified date". In PySpark 3.5.3 runs, `calculate_means`, `standardize_data`, `univariate_analysis`, `handle_missing`, `correlation_analysis` stopped on a date column. `rolling_window_analysis` averaged a time-stamp as Unix seconds. In a session on America/Whitehorse time, 1960-01-01 00:00 became -315586800.0 (-315619200.0 in UTC), where SAS gives 0. `correlation_analysis` took booleans as 0 and 1, while the other numeric methods refused them. The class should turn dates and time-stamps into SAS values or refuse them with 1 clear error. It should treat booleans the same way in every method.

- `univariate_analysis` returns Spark's population skewness and kurtosis, with percentiles from `approxQuantile` at a relative error of 0.01. PROC UNIVARIATE defaults to `VARDEF=DF` and to exact percentiles by definition-5. On the sample ages, it therefore gives a median of 53.5 where the method returns 52. The method also returns no N, which heads the Moments table of PROC UNIVARIATE's default output. It should add N. SAS's list of ODS tables marks BasicMeasures, ExtremeObs, Moments, Quantiles, TestsForLocation as default. SAS therefore also shows, among others, the mode, the variance, the range, the interquartile range, the standard error of the mean, the 5 extreme values at each end, the tests for location. The method returns 15 statistics, none of these. It should add them. Otherwise, its docstring should name the tables that it leaves out. Its result also passes through pandas, which turns a statistic that Spark leaves NULL into NaN. On 1 row, a PySpark 3.5.3 run gave NaN for the standard deviation, the skewness, the kurtosis. 4.3.0, with Arrow on, kept them NULL. SAS has no NaN. The method should build its result in Spark. The default Moments table also holds "Sum Weights", "Sum Observations", "Uncorrected SS", "Corrected SS", "Coeff Variation". SAS prints the MissingValues table when missing values exist: its table list marks it "Default, if missing values exist". The method returns neither. SAS also leaves skewness missing below 3 values and kurtosis below 4. For skewness: "If VARDEF=DF, then n must be greater than 2." For kurtosis: "If VARDEF=DF, then n must be greater than 3." In a PySpark 3.5.3 run on 2 values, the method gave a skewness of 0.0 and a kurtosis of -2.0. Its output types also differ by version -- `min` and `max` of an integer column came back as `bigint` on 3.5.3 and `int` on 4.3.0 because 4.3.0 turns Arrow on for pandas.

- `rank_data` has no rank for SAS's default `TIES=MEAN`, which gives tied values the mean of their ranks, nor for `TIES=HIGH` or `TIES=LOW`. Its default should be `TIES=MEAN`, as in PROC RANK. Its `method='percent'` uses `percent_rank`, which gives (rank - 1) / (n - 1), from 0 to 1. PROC RANK's `PERCENT` divides each rank by the count of non-missing values and multiplies by 100, with `TIES=HIGH` as its default there. The method also has no option for `GROUPS=`, which "assigns group values ranging from 0 to number-of-groups minus 1" by `FLOOR(rank*k/(n+1))`. Spark's `ntile` does not match it. On 1, 1, 1, 1, 2, 3, 4, 5, 6, 7 with 4 groups, a PySpark 3.5.3 run of `ntile` put the 4 tied 1s in 2 groups, where the formula puts them all in group-0. The method should add a groups option with PROC RANK's formula. It also ranks only from smallest to largest. PROC RANK's `DESCENDING` option "reverses the direction of the ranks", such that the largest value gets rank-1. The method should take a descending option. It also returns the rows in a new order. In a PySpark 3.5.3 run, ids 1 to 5 came back as 3, 5, 2, 4, 1. The `OUT=` listing in SAS's own PROC RANK example keeps the input order, with the ranks unsorted beside it. The method should restore the input order.

## New SAS equivalents

- DATA-step BY-group processing with `FIRST.` and `LAST.` flags. With several BY variables, "SAS sets the value of FIRST.variable to 1 for the variable whose value changed, as well as for all of the variables that follow in the BY statement." A flag that tests only its own column gave 0 where SAS gives 1. The method should follow SAS's rule.

- `LAG` through `lag` over an ordered window and 2 `RETAIN` patterns (a running total and a value carried forward) through cumulative windows. Spark's `lag` matches `LAG` only when `LAG` runs on every row: "An occurrence of the LAGn function that is executed conditionally will store and return values only from the observations for which the condition is satisfied." A running total needs SAS's 2 forms. The sum statement treats a missing value as 0, which a cumulative `sum` matches. `RETAIN tot 0; tot = tot + x;` turns missing from the 1st missing value on. Each needs its own option.

- `PROC APPEND` and DATA-step `SET` with several input data-sets. `SET` matches columns by name: "The values of variables found in one data set but not in another are set to missing." Spark's `union` matches by position and crossed the values of 2 columns in another order without an error. `SET` needs `unionByName(allowMissingColumns=True)`. `PROC APPEND` needs `FORCE` for a column that the base data-set lacks. The method should therefore raise an error unless asked to drop that column.

- `PROC SQL` queries across several DataFrames (`sql_query` registers only 1 view, `temp_table`).

- `PROC COMPARE`: compare 2 DataFrames by key and report the rows and values that differ, such that converted code can be checked against a SAS output exported to CSV. PROC COMPARE matches rows by position unless an `ID` statement names keys: "In a simple comparison, PROC COMPARE uses the observation number to determine which observations to compare." Its rule that "a missing value is judged equal only to a missing value of the same type" needs `eqNullSafe`. Its default `METHOD=EXACT` with `CRITERION=` options must be there since a CSV round trip changes the last digits of a double.

- The SAS date functions `INTNX` (with its alignment argument: `BEGINNING`, `MIDDLE`, `END`, `SAME`) and `INTCK` (with its `DISCRETE` and `CONTINUOUS` methods), through Spark date functions. `INTNX` aligns to `BEGINNING` by default, while Spark's `add_months` keeps the day, as `SAME` does. `INTCK` counts by `DISCRETE` by default: "For the DISCRETE method, the distance in months between January 31, 2000, and February 1, 2000, is one month." Spark's `months_between` gave 0.03. SAS weeks start on Sunday: "In general, weekly intervals begin on Sunday, and SAS counts a week whenever it passes a Sunday." Spark's week truncation starts on Monday. Each rule needs a test.

- DATA-step `ARRAY` with `DO` loops over a list of columns.

- `PROC IMPORT` and `PROC EXPORT` for CSV files, with Parquet as a 2nd format on the Spark side. PROC IMPORT guesses types from 20 rows by default (`GUESSINGROWS`) and turns a space in a column name into an under-score. "Occupancy Code" becomes Occupancy_Code. Spark's `inferSchema` reads every row and keeps the name. PROC EXPORT writes 1 file, while Spark's `write.csv` wrote a folder of part files. Both need options that follow SAS.
